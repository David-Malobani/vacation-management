# Vacation Management

A web application to request and validate vacations.

- **Requesters** submit vacation requests, follow their status, and edit or cancel requests that are still pending.
- **Validators** review every request on a filterable, paginated dashboard and approve or reject them. A rejection requires a comment. A decision made by mistake can be edited until the vacation starts.
- **Both roles** share a team planning calendar that shows who is off and when.

| Layer    | Stack                                                                                   |
| -------- | --------------------------------------------------------------------------------------- |
| Frontend | Vue 3, Vite, TypeScript, Vue Router, Pinia, Axios, Tailwind CSS v4                      |
| Backend  | Node.js, TypeScript, [CommonEventFramework](https://www.npmjs.com/package/commoneventframework) (CEF), Express (local HTTP host), zod, JWT |
| Database | PostgreSQL 16 with TypeORM (migrations, no `synchronize`)                               |
| Tests    | Vitest (business rules, command/event buses, transactional runner, input schemas)       |

## Quick start

Prerequisites: **Node.js 20+**, plus **Docker** *or* a local **PostgreSQL 16**.

```bash
npm install          # installs the root, server/ and frontend/ dependencies
npm run setup        # creates server/.env from server/.env.example
npm run db:up        # starts PostgreSQL in Docker (skip if you use a local Postgres)
npm run db:setup     # runs migrations + seeds demo data
npm run dev          # API on http://localhost:3000, app on http://localhost:5173
```

Open **http://localhost:5173** and sign in with a demo account. The login page can also fill them in for you.

## Installation

```bash
npm install
```

The root `postinstall` runs `npm install` in `server/` and `frontend/`. To install each app on its own, run `npm install` inside that folder.

## Database setup

The API reads its connection settings from `server/.env` (defaults: `postgres` / `postgres` on `localhost:5432`, database `vacation_management`).

**Option A: Docker**

```bash
npm run db:up        # postgres:16-alpine, waits until it is healthy
```

If port 5432 is already in use, run `POSTGRES_HOST_PORT=5433 npm run db:up` and set `DB_PORT=5433` in `server/.env`.

**Option B: local PostgreSQL**

```bash
createdb -U postgres vacation_management
```

**Then, in both cases:**

```bash
npm run db:setup     # = migrations + seed
npm run db:seed      # reset demo data at any time (truncates both tables)
```

The migration enables the `btree_gist` extension, which ships with PostgreSQL. It is used by the overlap constraint described below.

## API

All endpoints except login require `Authorization: Bearer <token>`. Errors always have the same shape:
`{ "error": { "code", "message", "details?" } }`, with status 400 (validation), 401, 403, 404 or 409 (business rule).

| Method & path                         | Role           | Description                                                    |
| ------------------------------------- | -------------- | -------------------------------------------------------------- |
| `POST /auth/login`                    | public         | Email and password → `{ token, user }`                         |
| `GET /auth/me`                        | any            | Current user                                                   |
| `GET /users?role=`                    | Validator      | Users (for the dashboard's employee filter)                    |
| `POST /vacation-requests`             | Requester      | Submit a request → 201                                         |
| `GET /me/vacation-requests`           | Requester      | Own requests. `?status=&page=&pageSize=`                       |
| `GET /vacation-requests`              | Validator      | All requests. `?status=&userId=&page=&pageSize=`               |
| `PUT /vacation-requests/:id`          | Requester      | Edit own **pending** request                                   |
| `DELETE /vacation-requests/:id`       | Requester      | Cancel own **pending** request → 204                           |
| `POST /vacation-requests/:id/approve` | Validator      | Approve a pending request. Optional `{ comment }`              |
| `POST /vacation-requests/:id/reject`  | Validator      | Reject a pending request. **Required** `{ comment }`           |
| `PUT /vacation-requests/:id/decision` | Validator     | Correct a decision made by mistake (approved ↔ rejected) before the vacation starts. `{ status, comment }`, comment required for Rejected |
| `GET /team/vacations?from=&to=`       | any            | Pending and approved vacations in a range (≤ 93 days)          |

Paginated responses: `{ items, page, pageSize, total, totalPages }` (default page size 10, max 100).

### Request flow (write side)

```
HTTP ─► Express (server.ts)          JSON body as text, CORS, logging, URL decoding
         └─► CEF handler (index.ts)   same function that runs on AWS Lambda
              1. getRouteConfig       matches root.yaml
              2. authorize            JWT + x-roles from root.yaml  → 401 / 403
              3. x-inputParser        zod validation → builds e.g. ApproveVacationRequestCommand
              4. x-handler            commandBus.dispatch(command)
                   └─► ApproveVacationRequestHandler
                        Transactional.run:  BEGIN
                          lock row (SELECT … FOR UPDATE) → business rules → save
                          record(VacationRequestApprovedEvent)
                        COMMIT ─► EventBus.publish ─► listeners (log)
              5. AppError → HTTP status + { error } body
```

Reads (lists, team calendar) are plain query functions: they change nothing, so they skip the bus, the transaction and events (a light CQRS split).

### Business rules: where each one is enforced

| Rule                                         | Frontend (UX)                  | API                                                     | Database (last line of defence)                |
| -------------------------------------------- | ------------------------------ | ------------------------------------------------------- | ---------------------------------------------- |
| 1. End date after start date                 | Form validation, `min` on input | `assertEndAfterStart`                                   | `CHECK (end_date > start_date)`                |
| 2. No overlapping requests for the same user | –                              | `hasOverlap` query (pending and approved only)          | `EXCLUDE USING gist (user_id =, daterange &&)` |
| 3. Approved requests cannot be modified      | Edit/Cancel only on pending    | `assertModifiable` in Update/Cancel handlers            | –                                              |
| 4. No requests in the past                   | Form validation, `min` on input | `assertNotInPast`                                       | –                                              |
| 5. A rejection must have a comment           | Required field in dialog       | zod schema + `assertRejectionComment`                   | `CHECK`: rejected ⇒ non-blank `comments` |
| 6. Only validators approve or reject         | Validator-only routes/buttons  | `x-roles: [Validator]` in root.yaml                     | –                                              |

Additional rules: only pending requests can be approved or rejected, a validator can correct a decision (approved ↔ rejected) only until the vacation starts, a requester can only change their own requests (403), and only requesters submit requests.

## Technical decisions

- **CEF owns routing, Express owns HTTP.** All routes, their handlers and their access rules are declared in `root.yaml`, and `index.ts` is CEF's standard entry point, so the API can be deployed unchanged to AWS Lambda with `cef-build` (verified by invoking the bundle with API Gateway v2 events). CEF's own dev server is fairly minimal (it doesn't URL-decode query strings and has no middleware), so locally a small Express app (`server.ts`) receives HTTP, converts it into a `CommonEvent` and calls the same handler. Express is the only difference between local and Lambda.
- **Declarative access control.** Each route in `root.yaml` uses the OpenAPI `security` field (JWT required by default, `security: []` for public routes) plus an `x-roles` extension. The entry point enforces both before any parser or handler runs. The same file also produces the Swagger docs at `/doc`. Ownership checks (e.g. "your own request") need data, so they live in the command handlers.
- **Commands and events.** Every state change is a command with exactly one handler, registered in one place (`container.ts`). HTTP handlers only build commands and dispatch them, so the same commands could be triggered from SQS or a CLI. Handlers run inside `Transactional`, which **publishes events only after COMMIT**. A rolled-back change therefore never notifies anyone, and a failing listener never breaks the command.
- **Rules as pure functions + database constraints.** The rules have no I/O, which makes them easy to unit test. The database constraints guarantee them even when two requests race: two overlapping submissions arriving at the same time are stopped by the `EXCLUDE` constraint, which the repository maps to the same 409 error. Approve, reject, update and cancel lock the row (`FOR UPDATE`), so two validators cannot both decide the same request.
- **Correcting a decision is a separate command.** Rule 3 is read as "a requester can never modify an approved request". A validator who clicked the wrong button can flip the decision with `ChangeVacationRequestDecisionCommand`, but only before the vacation starts. Changing to rejected still requires a comment, re-approving checks overlaps again, and every correction emits `VacationRequestDecisionChangedEvent` with the previous status, so the log shows who changed what.
- **Validation at the edge with zod.** Malformed input gets a 400 with every issue listed under `details`. Business violations get a 409 with a readable message.
- **Dates are `DATE` columns exchanged as `YYYY-MM-DD` strings.** No timezone conversion happens anywhere, so a vacation never shifts by a day. ISO dates also compare correctly as strings.
- **Pagination** uses offset/limit with a total count, filtered in SQL and backed by an index on `(status, created_at)` and on `user_id`.
- **Frontend.** Axios goes through a Vite proxy (`/api`), so there is no CORS in development. The Pinia store restores the session after a reload. Route guards use `meta.roles`. The dashboard keeps its filters in the URL, so a filtered view survives a reload. Shared components (table, form, dialog, pagination) are used by both roles' pages. The team calendar hides reasons and comments, because colleagues only need to see dates.

## Known limitations

- **A one-day vacation is not possible**, because rule 1 is applied literally (the end date must be strictly after the start date). Durations are counted in calendar days; weekends and public holidays are not excluded.
- **Events are in-process and not durable.** If the process stops right after a commit, the events of that transaction are lost. A production version would use an outbox table and a queue (e.g. SQS, which CEF already supports). The only listener today writes a log line; e-mail notifications are not implemented.
- **Authentication is minimal.** Demo users are seeded and there is no sign-up, password reset or refresh token. The JWT is kept in `localStorage` (simple, but readable by injected scripts) and logging out does not revoke it before it expires (8h).
- **Cancelling deletes the row.** No history is kept besides the event log.
- **"Today" uses the server's timezone** when checking for past dates.
- **No teams or departments.** Every validator sees everyone, and the calendar shows the whole company (a range of at most 93 days per call).
- **CEF quirks.** `npx cef-gen-handlers` / `cef-build` do nothing in this setup, because the bin entry's "run directly" check fails through the npm symlink. The npm scripts therefore call the CEF scripts by file path.
- **The Lambda deployment itself is not set up** (no infrastructure as code). Only the bundle and the handler were verified.
